# Phase 6 — deterministic mock content + matching engine

This is a **mock-only** phase: no real AI, no real backend, no live sync with `safespeak-admin`, no production database. Its purpose is to make the eventual real integration a drop-in replacement for what's here, not a redesign.

## What's real vs. what's mock

- **Real, unchanged this phase**: the five Assistant entry routes, the demo Assistant conversation (`src/lib/demo-assistant-conversation.ts`), the Assistant→Triage transition (`saveAssistantTriageSource`, `src/lib/assistant-triage.ts`), the Triage page's existing design/layout/components.
- **Mock, new this phase**: everything under `src/lib/mock/`, plus the generated/copied files at `src/lib/contract/` and `src/lib/matching-rules/`.
- **Not real AI**: the demo Assistant conversation was already a deterministic keyword/stage machine before this phase (see `src/lib/demo-assistant-conversation.ts`) — Phase 6 does not add any conversation-text classification. `src/lib/mock/incident-context.ts` explicitly never inspects free-text chat content.

## The five Assistant topics

`src/lib/mock/topic-registry.ts` defines `AssistantTopicKey = "general_assistant" | "domestic_violence" | "racial_abuse" | "cyber_scam" | "migrant_challenges"`, matching the `topic` query param on all five `/dashboard?view=assistant&topic=...` routes. Each topic has a display label, a `mockScenarioId`, and a short list of *candidate* Incident Type/Triage Label machine keys — a best-effort hint only, resolved against whatever the loaded content bundle actually contains and silently dropped if absent. **Topic-based matching never depends on this resolution succeeding**: a Matching Rule's `topicKeys` condition is matched directly against `context.assistantTopic`, so a rule scoped only to a topic (no incident-type/triage-label condition) still triggers correctly even against an empty/placeholder bundle.

## Canonical contract + generated files (do not hand-edit)

`src/lib/contract/published-content-contract.ts`, `src/lib/matching-rules/engine.ts`, and `src/lib/contract/generated/published-content-bundle.json` are **copied byte-for-byte from `safespeak-admin`** by `safespeak-admin/scripts/generate-mock-bundle.ts`. To change any of them, edit the `safespeak-admin` originals and re-run `pnpm tsx scripts/generate-mock-bundle.ts` from `safespeak-admin/`, then re-run `pnpm mock-bundle:validate` here to confirm.

Schema version `"1.0.0"`, purpose `"published_content"` (an Admin Backup bundle, `purpose: "admin_backup"`, is explicitly rejected by `MockContentRepository`).

## Mock architecture (`src/lib/mock/`)

```
content-repository.ts   -> ContentRepository interface, MockContentRepository, FutureApiContentRepository (placeholder)
topic-registry.ts       -> AssistantTopicKey definitions
incident-context.ts     -> buildMockIncidentContext(repository, input): MockIncidentContext
triage-adapters.ts      -> PublishedX -> presentational-prop mapping functions (pure, no React)
triage-mock-types.ts    -> TriageAdvocateCard, TriageReportingDestinationCard (no existing type fit)
triage-recommendation-service.ts -> TriageRecommendationService / MockTriageRecommendationService
```

`ContentRepository` is the interface every consumer depends on — never the raw bundle import or (never) Admin's IndexedDB directly. `MockTriageRecommendationService.getRecommendations({ topic, timeline })`:
1. Builds a `MockIncidentContext` (topic + a small allow-list of exact-match `AssistantTimeline` fields already collected by the existing demo conversation — never free-text parsing).
2. Runs `runMockMatching()` from the copied `engine.ts` against the full bundle.
3. Resolves each matched record via the repository and maps it through the adapters into `TriageResourceGroup`/`TriageSupportOption`/`TriageAdvocateCard`/`TriageReportingDestinationCard`.

## Triage page integration

`src/components/dashboard/dashboard-report-submission-pages/report-submission-support-page.tsx` — in the existing "no live backend session" (demo) branch. A `mockTriage` state and `shouldShowMockTriage` boolean gate a JSX block that is the **single** recommendation source for this branch (see "Phase 6.1 — single-source consolidation" below — Phase 6 originally added it as an *additive* sibling next to the old static catalogue; Phase 6.1 removed the duplicate). Sections: two `TriageResourceGroup`s ("Suggested guides" from matched Microcards, "Rights & Legal Information" from matched Rights Content, reusing the existing `ResourceCard`), "Support options tailored to you" (matched Organisations, reusing `TriageSupportOptionCard`), "Advocates & Counsellors" and "Reporting Destinations" (two new card components in `triage-mock-cards.tsx`, since no existing presentational type covered verification status or the anonymous/emergency tri-state). The pre-existing `conversationSessionId`-present (live backend) branch explicitly clears `mockTriage` — mock recommendations never apply there, and `shouldShowMockTriage`/`shouldShowSupportOptions` are mutually exclusive by construction (`!triage` vs `Boolean(triage)`).

An empty match category is simply omitted (no section rendered) — never backfilled with the old generic hardcoded list and never shown as a disruptive empty-state box, per the mock-matching empty/error policy. Independently-required emergency guidance (the Triple Zero card) is rendered from its own `emergencyOptions` derivation, gated on the shared no-session boundary alone — never on whether a matching rule happened to fire.

## Phase 6.1 — single-source consolidation, five-topic completeness, canonical conversation state

Phase 6.1 closed three gaps left after Phase 6's initial integration:

### 1. Single recommendation source (no more duplicate catalogue)

Phase 6 added the governed mock sections as a *sibling* block next to the pre-existing static `demoTriage.resourceGroups`/`demoTriage.supportOptions` (from `src/lib/triage-view-model.ts`'s `buildStandardTriageResourceGroups()`/`buildDemoSupportOptions()`) — both could render at once, showing duplicate/parallel "Get Support"/"Know Your Rights"/"Support options" sections. Phase 6.1 removed that duplicate rendering from the Triage page: `demoTriage`'s intro copy and "Your options" (`primaryActions`) navigation block are unchanged (non-recommendation UI copy), but its `.resourceGroups`/non-emergency `.supportOptions` are no longer rendered — the governed `mockTriage` pipeline is now the only recommendation source. `buildStandardTriageResourceGroups()`/`buildDemoSupportOptions()`/`buildDemoTriageOverview()` themselves were **not** deleted — they are still used by `src/components/dashboard/dashboard-report-submission-pages/report-review-onboarding-pages.tsx` and `src/lib/report-builder-view-model.ts`, unrelated reporting-flow code out of this phase's scope. The Triple Zero emergency entry from `buildDemoSupportOptions()` is still shown, filtered out and rendered independently (see above) rather than dropped along with the rest of that array.

### 2. Five-topic matching-rule coverage

Verified against the real deterministic engine + generated bundle: with a bare-topic `MockIncidentContext` (no jurisdiction/urgency/triage-label refinement — what the Assistant routes produce by default), only `cyber_scam`(disabled), `general_assistant`, and `migrant_challenges` previously produced zero results; `domestic_violence` and `racial_abuse` also turned out to produce zero, since their Admin-seeded rules' jurisdiction/urgency/triage-label conditions were never reliably satisfiable by default context. Fixed on the `safespeak-admin` side (new topic-only-conditioned baseline rules per topic) — see `safespeak-admin/docs/ARCHITECTURE.md` "Phase 6.1 — five-topic matching-rule coverage" for the exact rules added. Also fixed `topic-registry.ts`'s candidate Triage Label/Incident Type machine keys, which had drifted from the real seeded taxonomy (see the same admin doc, "matching-rule/context parity").

### 3. Canonical Assistant conversation state

Two confirmed bugs in `src/lib/demo-assistant-conversation.ts`, both now fixed:

- **Seeded vs. typed divergence**: `resetDemoConversation()` (used to seed a conversation from a `?message=...`/`prefillMessage` URL param) used to be a second, hand-duplicated copy of the "opening" stage's transition logic, and stayed on `stage: "opening"` forever for a non-hijab seeded message instead of advancing to `"initial_clarification"` the way the identical text typed manually would. The next turn then silently re-processed whatever the user typed next as if it were still the very first message. Fixed by making `resetDemoConversation()` delegate to the same internal `getScenarioResponse()` every manually-typed turn already uses — there is now exactly one place that decides what happens to an "opening" stage message, seeded or typed.
- **Missing Triage handoff for the main storyline**: `handleContinueToTriage()` requires `demoState.understanding`, but only the hijab-keyword storyline ever set it (via `buildHijabUnderstanding`) — the general (non-hijab) storyline reaching `final_result` had no `understanding` and no wiring at all from its "Continue to next steps" suggestion to `handleContinueToTriage()` (it just re-sent the click as a chat message, which the state machine replied to with "The demo result is already available above..." forever). This meant four of the five Assistant topics had **no working path to Triage** unless the conversation happened to mention "hijab". Fixed with a new `buildFinalStoryUnderstanding()` (the general storyline's counterpart to `buildHijabUnderstanding` — deterministic and scenario-driven, matching `buildFinalResult()`'s own already-hardcoded narrative, never inferred from raw keywords) and by wiring the exported `CONTINUE_TO_TRIAGE_SUGGESTION_ID` suggestion the same way `HIJAB_CONFIRM_TRIAGE_SUGGESTION_ID` already was in `dashboard-assistant-pages.tsx`'s `handleSuggestionClick`.

## Phase 7 — recommendation details, safe actions, and complete mock user flows

Phase 7 makes every governed recommendation rendered by the `mockTriage` pipeline (above) fully clickable through to a safe, typed detail view, instead of several cards having no click target at all (Microcards with a `view_*`/`start_report`/`none` CTA) or a hardcoded generic link (Rights Content always pointed at `/dashboard?view=resources`). It adds no new recommendation source, no new Triage page, and no live Admin→Frontend sync — everything still resolves from the same generated bundle via `ContentRepository`.

### New files (`src/lib/mock/`)

- `recommendation-types.ts` — the one typed discriminated union (`MockRecommendation` = `MicrocardRecommendation | RightsContentRecommendation | SupportOrganisationRecommendation | SupportProfessionalRecommendation | ReportingDestinationRecommendation | LegislationSourceRecommendation`), each carrying `entityId`, `matchReasons: string[]` (plain-language only), `sourceBundleVersion`, and the full typed `PublishedX` record. `RECOMMENDATION_DOMAIN_BY_ENTITY_TYPE` is the single source of truth mapping an entity type to exactly one `ContentDomain`, so an id can never resolve against the wrong collection.
- `recommendation-resolver.ts` — `resolveRecommendation(entityType, entityId, matchReasons?, repository?)` is the **only** place a recommendation is looked up. Returns `{status: "found" | "not_found" | "unsupported_entity_type"}` — never throws, never fabricates a record when the id doesn't resolve.
- `safe-actions.ts` — the one place phone/email/URL/internal-route safety is decided: `safeDialablePhone`/`phoneHref`, `safeEmail`/`emailHref`, `safeHttpsUrl` (rejects `http:`/`javascript:`/`data:`, accepts only `https:`), `safeInternalRoute` (a hand-maintained allow-list, `INTERNAL_ROUTE_MAP`, translating the Admin Microcard CTA's abstract route keys — `/`, `/rights`, `/support`, `/report`, `/resources`, `/emergency` — into real Dashboard routes), and `buildContactActions()` (only ever returns actions actually backed by valid source data). `REPORT_START_FROM_TRIAGE_HREF` is the one confirmed "start a report from Triage" route (`/dashboard?view=reportsubmissiondetails&fromTriage=1`, already used twice elsewhere on this page before Phase 7) — reused everywhere a Microcard/detail view needs to send someone into the report flow, never a second competing route.

### Shared recommendation detail shell

`src/components/dashboard/dashboard-report-submission-pages/recommendation-detail-modal.tsx` — one `RecommendationDetailModal` shell (accessible `role="dialog"`/`aria-modal`, focus trap, Escape-to-close, backdrop-click-to-close, focus restored to the trigger on close) with 6 typed content-body renderers switched on `entityType`, reusing the existing `MicroCardDetailOverlay` overlay pattern already established on this same page rather than inventing a new one. Renders only safe public fields (never internal notes/verification notes/audit events/matching-rule ids/scores — there is nothing in `PublishedX`/`MockRecommendation` to leak in the first place, since the public contract never carries them). A Microcard's own CTA (all 7 canonical types) becomes a secondary action inside its detail body — `view_rights_information`/`view_legislation_source`/`view_support_service` navigate to another entity's detail *within the same modal* (with a "Back" affordance once there's somewhere to go back to), `start_report` links to `REPORT_START_FROM_TRIAGE_HREF`, `open_internal_route`/`open_safe_external_link` go through `safe-actions.ts`, and `none` (or an unresolved target) renders no button at all rather than a dead or fabricated one.

The Reporting Destination detail view is intentionally **view-only** in this phase (contact/online-report actions only) — it does not add a "select this destination for my report" action, since that would require auditing and safely wiring the report draft's destination-selection step, which is out of this phase's scope. This trivially satisfies the "viewing a destination must never auto-select it" requirement by not offering selection from here at all.

### Wiring

`report-submission-support-page.tsx`'s `ResourceCard` and `TriageSupportOptionCard`, and `triage-mock-cards.tsx`'s `TriageAdvocateCardView`/`TriageReportingDestinationCardView`, each take an optional `onOpenDetails` callback. It is only ever passed from the `shouldShowMockTriage` render block (the governed pipeline) — never from the unrelated hardcoded `emergencyOptions`/legacy `demoTriage` call sites reusing the same components, so those never expose a "View details" action for an id that doesn't exist in the mock bundle. The detail selection is local `useState` on the Triage page itself (`{entityType, entityId, matchReasons} | null` plus a small in-modal back-stack), rendered as an overlay on the same page — Triage scroll position, topic, and result set are untouched by opening/closing it. `TriageResourceItem`/`TriageSupportOption` gained an additive optional `matchReasons?: string[]` field (populated only by the mock adapters; legacy/demo builders simply omit it).

### Tests

`tests/unit/recommendation-resolver.test.ts`, `recommendation-types.test.ts`, `safe-actions.test.ts` (resolver domain-isolation/not-found/unsupported-type behaviour, the entity-type↔domain bijection, and every safe-action validator's accept/reject cases). `tests/e2e/triage-recommendation-details-smoke.spec.ts` covers opening a Microcard's detail modal, Escape/Close-button/backdrop-click dismissal, and a support organisation's verification-status rendering — run directly (not part of the full historical suite), same convention as `assistant-to-triage-five-topics.spec.ts`.

## Phase 7.1 — persistent recommendation navigation, explicit destination selection, professional media safety

Phase 7.1 closes the gaps Phase 7 explicitly deferred: recommendation detail state was component-local only (lost on refresh, invisible to Back/Forward, not linkable), Reporting Destination detail was view-only with no way to actually use a destination in the report flow, and professional photos always fell back to initials with no safety-validated rendering path.

### Report-flow audit (done first, before any implementation)

The canonical report draft is `ReportFlowDraft` in `src/lib/report-flow.ts`, stored under the `sessionStorage` key `safespeak_report_flow_draft`, read/written only through `getResolvedReportFlowDraft()` / `saveReportFlowDraft()` / `mergeReportFlowDraft()` (latest-edits-win: `mergeReportFlowDraft` spreads `defaultReportFlowDraft` → the current resolved draft → the partial update, so an unrelated update never drops existing fields). The destination field is `selectedDestinationId` (+ `selectedDestinationName`, `selectedDestinationSource: "backend" | "manual"`) — confirmed by `DestinationStage` in `report-review-onboarding-pages.tsx`, the pre-existing guided-onboarding flow's own destination step, whose `handleSelect()` calls `mergeReportFlowDraft({ selectedDestinationId: option.id, selectedDestinationName: option.name, selectedDestinationSource: option.source, jurisdiction })` — Phase 7.1's Triage-side selection reuses this exact field/helper with `selectedDestinationSource: "manual"` (never `"backend"`, since it isn't sourced from `getReportDestinations()`).

**Important seam, documented rather than silently "fixed"**: `report-submission-review-page.tsx` / `report-submission-share-page.tsx` (the advanced/manual report-flow pages) cross-reference `selectedDestinationId` against their own `destinationOptions`/`AuthorityMatch` catalogue (`src/lib/report-authority-routing.ts`, a fixed backend-style routing list with its own `destinationId` key space — police/eSafety/Legal Aid/etc, unrelated to the Triage mock bundle's `PublishedReportingDestination.id`). A Triage-selected mock destination's id will not match an entry in that catalogue, so those two pages' own "is this destination in my list" UI will not visually highlight it (though `selectedDestinationName` still renders wherever the code reads it unconditionally, e.g. `report-review-onboarding-pages.tsx`'s destination stage, which is the actual page reached via `fromTriage=1`). Unifying the two destination catalogues would be a report-flow redesign, explicitly out of this phase's scope — the draft field itself is written correctly and canonically either way.

**Canonical report-start route**: `report-submission-details-page.tsx`'s `activeStep` already falls back to `"report"` whenever `fromTriage=1` is present with no `step`, and a `useEffect` there immediately `router.replace`s to the explicit `stepHref("report", true)` form anyway — so the old bare `&fromTriage=1` link and `&step=report&fromTriage=1` were always behaviourally identical, just one extra client redirect apart. `REPORT_START_FROM_TRIAGE_HREF` (`src/lib/mock/safe-actions.ts`) now uses the explicit form (`/dashboard?view=reportsubmissiondetails&step=report&fromTriage=1`), matching `stepHref()`'s own canonical output and `report-submission-incident-review-page.tsx`'s pre-existing real usage of that exact string. Every "start a report from Triage" call site (`triage-view-model.ts`, `report-submission-support-page.tsx`, the Microcard `start_report` CTA, `safe-actions.ts`'s own `INTERNAL_ROUTE_MAP["/report"]`) now imports this one constant — no duplicated literal route remains.

### URL-backed recommendation-detail state contract

`src/lib/mock/recommendation-detail-url.ts` defines the contract: two flat query params on the existing `/dashboard` route, reusing the same convention as `step`/`fromTriage`/`conversationSessionId` rather than inventing a routing framework —

- `recommendationType` — the stable entity type string.
- `recommendationId` — the stable entity ID string.

Never the full record, match reasons, contact details, or content body. `report-submission-support-page.tsx` derives `detailSelection` directly from `useSearchParams()` every render (no local `useState` for *which* detail is open) — this is what makes Back/Forward/refresh/direct-link all work for free, since Next's router re-renders the component reactively on every history navigation. Match reasons are never put in the URL; a small opportunistic in-memory cache (`openedWithMatchReasons`) shows them only when a card was just clicked in the current session, and is silently absent after a refresh, Back, Forward, or direct link — an accepted, documented mock-only limitation, not a bug.

**History behaviour**: opening a detail (from a card, or navigating to a nested target from within the modal) always calls `router.push(..., { scroll: false })` — including nested navigation, which deliberately creates a new history entry rather than replacing the current one, because Back is required to restore the *previous* nested detail (Microcard → Rights → Legislation → Back → Rights → Back → Microcard → Back → closed). Closing (Close button / Escape / backdrop click) also pushes a clean URL rather than calling `history.back()`, so it behaves identically whether the detail was reached by clicking through Triage or via a direct/refreshed link — going back from a directly-loaded detail must never leave the SafeSpeak app. `{ scroll: false }` is passed on every push/replace to satisfy "must not scroll unexpectedly to the top." The in-modal chevron "Back" affordance (from Phase 7) now calls `router.back()` and is only shown when a `detailStackDepth` counter (incremented on nested navigation, reset on a fresh top-level open or on close) is greater than zero.

Recommendation details are gated on `shouldShowNoSessionTriage` (no live `conversationSessionId`) — mock/live-session separation is preserved regardless of what a stray `recommendationType`/`recommendationId` query param says.

### Reporting Destination: view vs. select vs. submit

Three distinct, never-conflated actions on a Reporting Destination's detail body:

- **View details** — always informational only; never touches the report draft.
- **Use this reporting option** — calls `mergeReportFlowDraft({ selectedDestinationId: record.id, selectedDestinationName: record.name, selectedDestinationSource: "manual" })`. Stores only the stable id/name/source, preserves every other draft field (idempotent — selecting the same destination twice is a no-op merge), never sets `consentGranted` or `latestSubmissionId`, never navigates. Withdrawn (not shown) once already selected — a "Selected for this report" status pill (`role="status"`) is the only selected-state indicator, never a second/duplicate selection control.
- **Report online** (a `buildContactActions` contact action, when the destination has a public `onlineReportingUrl`) — opens the destination's own external URL in a new tab; structurally and behaviourally unrelated to draft selection.

Reopening the same destination later reads `getResolvedReportFlowDraft()?.selectedDestinationId` fresh (via a `useState` initializer on a component keyed by `recommendation.entityId`, so switching between two different destinations always re-reads the real draft state rather than carrying over stale local state) — the selected indicator is never just optimistic local UI.

### Professional profile images

Audited `PublishedSupportProfessional.profilePhoto` (`src/lib/contract/published-content-contract.ts`): it is file *metadata* only (`{fileName, fileSizeBytes, fileType}`), never a resolvable public path or URL. The committed generated bundle has exactly one professional with this field populated (`demo-counsellor-jordan-blake`, `jordan-blake-demo.jpg`), and no such asset file exists anywhere in either repo. **This is a real, current contract limitation, not something Phase 7.1 fabricated a workaround for**: `safePublicImageSrc()` (`safe-actions.ts`) and `ProfessionalAvatar` (`recommendation-detail-modal.tsx`) implement the full safe-rendering path (same-origin `/`-prefixed path or validated `https://` URL only; rejects `blob:`/`file:`/`data:`/`javascript:`/a Windows drive-letter path/protocol-relative URLs; `next/image` with `onError` falling back to initials; decorative `alt=""` since the name is already the modal's visible heading) so the component is ready the moment a real public asset path is added to the contract — but for every professional in the current fixture, rendering correctly falls back to initials today. No Admin media-architecture change or new public asset was added this phase (no genuine contract gap to fill yet — there's no path field to add an asset *for*).

### Tests

`tests/unit/recommendation-detail-url.test.ts` (parse/build/strip the two query params, preserves unrelated params, never carries more than the two keys), `report-flow-destination-selection.test.ts` (against a `sessionStorage` polyfill — merge preserves existing fields, idempotent re-selection, never sets consent/submission, replacement doesn't discard unrelated data), `recommendation-detail-modal-structure.test.ts` (structural source assertions: every `DetailBody` branch keyed by `entityId`, professional images only via `safePublicImageSrc`, no admin-only field names, "Use this reporting option" structurally separate from "Report online", no fabricated success states), plus new cases appended to `safe-actions.test.ts` (`REPORT_START_FROM_TRIAGE_HREF`'s exact value, `safePublicImageSrc` accept/reject matrix). `tests/e2e/triage-recommendation-persistence-smoke.spec.ts` covers nested Microcard→Rights→Legislation navigation with Back/Back/Back/Forward, refresh-restores-nested-detail, invalid id/entity-type direct links, close-preserves-unrelated-params, and the full destination view→select→persist-on-reopen flow — seeded via a direct `sessionStorage` write of `AssistantTriageSource` (the same shape `saveAssistantTriageSource()` writes) rather than the Assistant conversation UI, because the hijab-shortcut conversation's resulting `incidentCategory` does not correspond to the five `AssistantTopicKey` values and always resolves to the same generic match set — confirmed directly against the matching engine, not guessed.

## Phase 7.2 — canonical Reporting Destination handoff across the report flow

Phase 7.1 added "Use this reporting option" on Triage's Reporting Destination detail, but only as far as writing `ReportFlowDraft.selectedDestinationId` — it explicitly flagged as a known limitation that later report-flow pages might not resolve that id. Phase 7.2 closes that gap for the flow Triage actually feeds into.

### Route audit finding: two entirely separate report flows share one page

`report-submission-details-page.tsx` hosts **two distinct step machines** behind the same `view=reportsubmissiondetails` route, switched on the `step` query param: its own 6-step onboarding (`language/community/information/privacy/services/report`) and, once a `step` matches a `ReportReviewOnboardingStepId`, the **onboarding router** (`report-review-onboarding-pages.tsx`: `review→next→preview→destination→consent→complete`). `fromTriage=1` (with no `step`) defaults into the `"report"` step of the *first* machine, which is a dead end for a Triage-selected destination — the onboarding router's `DestinationStage`/`ConsentStage`/`CompleteStage` are the actual pages that read/display `selectedDestinationId`. Separately, `report-submission-review-page.tsx` + `report-submission-share-page.tsx` (`view=reportsubmissionreview`/`reportsubmissionshare`) are a **third, fully independent "advanced" flow** that is backend-exclusive (`getReportDestinations()`/`submitReportToDestination()` are real `apiRequest` HTTP calls; the local `REPORT_SUBMISSION_MOCK_MODE` fallback in `report-submission-mock.ts` is hardcoded `false`, i.e. dead code today). This phase's scope is the onboarding router, since that's what `fromTriage=1` actually reaches — the advanced review/share pages are an existing live/backend branch, preserved untouched per "do not replace backend destination API code with mock data."

### Four destination shapes, three ID namespaces (confirmed, not guessed)

1. **Governed mock bundle** — `PublishedReportingDestination`, resolved via `MockContentRepository`. IDs like `demo-destination-community-helpline`.
2. **Backend catalogue** — `ReportDestinationPreview` from `getReportDestinations()` (`src/lib/reports-client.ts`), IDs like `"nsw-police"`/`"esafety-commissioner"`.
3. **Onboarding router's own manual fallback** — `DestinationOption` (`src/lib/report-review-onboarding.ts`), built from `buildManualDestinationOptions(overview)` off *Triage-service-derived* data (`id: "manual-${service.id}"`) — a fourth, unrelated id shape, despite superficially looking "triage-related."
4. **`report-authority-routing.ts`'s `AuthorityMatch`** — a derived scoring/formatting layer over catalogue 2 only, with `legacyDestinationAliases` bridging a small set of hardcoded ids (`"mock-police"`→`"nsw-police"` etc) — it has no knowledge of catalogue 1 at all, so a governed-bundle id passed through `resolvePreferredDestinationId()` silently falls through unresolved rather than erroring.

`selectedDestinationSource` (`ReportFlowDraft`) was the union `"backend" | "manual"` — written only by the onboarding `DestinationStage` and Triage's modal (both wrote `"manual"` for two semantically different origins) and **never read/branched on anywhere**. This was the root cause: nothing downstream could tell a governed-bundle selection apart from a manual-fallback one.

### The fix: one additive source value + one resolver + one view model + one update helper

- **`selectedDestinationSource: "backend" | "manual" | "mock_bundle"`** (`src/lib/report-flow.ts`) — additive, no migration needed; existing `"backend"`/`"manual"` drafts are unaffected.
- **`updateSelectedReportDestination({ id, name, source })`** (`report-flow.ts`) — the one shared writer, used by both Triage's "Use this reporting option" and the onboarding `DestinationStage`'s `handleSelect`/`handleSelectTriageDestination`. Selecting the *same* id again is a no-op beyond `updatedAt` (idempotent, consent/submission state untouched); selecting a *different* id clears `consentGranted`/`consentGrantedAt`/`consentMode`/`preparedSubmission`/`latestSubmissionId` — a prior consent for destination A must never silently carry over to destination B. There was no pre-existing destination-change invalidation policy anywhere in the codebase (grep-confirmed) — this is the one now in effect.
- **`resolveSelectedReportDestination(draft, repository?)`** (`src/lib/mock/report-destination-resolver.ts`) — `{status: "found"|"not_found"|"incompatible_source"|"unavailable"}`. Only ever resolves `selectedDestinationSource === "mock_bundle"` selections through `MockContentRepository`; a `"backend"`/`"manual"`/missing source returns `"incompatible_source"` so callers fall back to their existing (unmodified) cached-name display — this is what keeps the mock and backend branches from mixing.
- **`ReportDestinationViewModel` / `reportingDestinationToViewModel()`** (`src/lib/mock/report-destination-view-model.ts`) — the one typed, public-fields-only mapping (name, humanised type, jurisdictions, reporting methods, tri-states, instructions, disclaimer, `buildContactActions()`-derived contact actions), plus the shared `REPORT_DESTINATION_TRISTATE_LABEL` map (now used by both the Triage detail modal and the onboarding Consent stage — no more per-page tri-state label duplication).

### Per-stage behaviour

- **Triage "Use this reporting option"** now writes `source: "mock_bundle"` via the shared helper (previously wrote `"manual"`, indistinguishable from the onboarding page's own manual fallback).

## Phase 8.2 — Micro-card end-to-end audit and hardening

Phase 8.2 audited the Micro-card ("Microcard") pipeline end to end — `safespeak-admin` IndexedDB → publish eligibility → generated bundle → this app's `MockContentRepository` → the matching engine → Triage rendering → the recommendation detail modal → CTA. **Conclusion: the pipeline was already fully built and working** (Admin CRUD, status-graph publish workflow, eligibility gating, the `toPublishedMicrocardExport` public-field mapper, `generate-mock-bundle.ts`, bundle validation, and the Phase 7 detail/CTA architecture above). No parallel Microcard system was created; nothing here duplicates any of it. The concrete gaps found and fixed were narrow:

### Important: "Microcard" names two unrelated systems in this codebase

The governed pipeline documented in this file (`PublishedMicrocard`, sourced from the Admin-published bundle) is **not** the same thing as `src/lib/microeducation.ts`'s `MicroEducationItem` (a real backend API client — `/microeducation`, `/microeducation/categories` — feeding the separate `?view=microcards`/`?view=microeducation` browsing pages and the Triage page's unrelated live-session-only `SuggestedMicroCard` block). Phase 8.2 is scoped entirely to the former. The two share a name by coincidence, not by design; neither references the other's data.

### Fixes

1. **CTA safety unification** (`src/lib/mock/triage-adapters.ts`). `microcardToResourceItem()` previously assigned `TriageResourceItem.href` from `record.cta.target` **raw and unvalidated** for `open_safe_external_link`/`open_internal_route`, while the detail modal's `MicrocardDetailBody` validated the same two CTA types through `safeHttpsUrl`/`safeInternalRoute`. Currently harmless in practice (Triage's `ResourceCard` always uses `onOpenDetails` for a governed microcard match, never this raw `href`), but a real divergence from "card CTA and details CTA use the same canonical mapper." Fixed with a new exported `resolveMicrocardCardHref(cta)` that calls the exact same `safeHttpsUrl`/`safeInternalRoute` functions the detail modal calls — both surfaces can now never disagree on what's safe to link to.
2. **Raw jurisdiction values rendered in the detail modal** (`recommendation-detail-modal.tsx`). All 6 `DetailField`/jurisdiction call sites (Microcard, Rights Content, Legislation Source, Support Organisation, Support Professional, Reporting Destination) rendered the contract's lowercase machine codes (`"nsw"`, `"commonwealth"`) verbatim instead of a human-readable label — `cardType`/`organisationType`/etc. were already humanised via `humanizeKey`, jurisdiction was the one field that wasn't. Fixed with a new `formatContractJurisdiction`/`formatContractJurisdictionList` pair in `triage-adapters.ts` (dedicated lookup — `humanizeKey` alone would mangle state abbreviations, e.g. "Nsw" — falling back to `humanizeKey` only for a value outside the known 9-value contract enum), applied at all 6 sites.
3. **`/emergency` internal-route target resolved to the plain dashboard home**, not an urgent-help destination, despite the seeded Microcard's CTA being labelled "Get emergency help" — a truthfulness gap (`safe-actions.ts`'s `INTERNAL_ROUTE_MAP`). Fixed to resolve to the same Smart Dialler route (`/dashboard?view=smartdialler`) the map's own `/support` key already used — reusing an existing allow-listed route, not adding one.
4. **Safety Gate stacking bug, found via real Playwright testing of a direct/bookmarked Microcard detail link** (`src/components/safety/safety-gate.tsx`). The Safety Gate (`z-[120]`) could render *underneath* other full-screen app overlays already using `z-[130]`/`z-[140]` (the recommendation detail modal, Smart Dialer modal, an Assistant modal). In ordinary use this never mattered — the gate blocks all interaction before any other modal could be triggered — but a direct URL straight to `?recommendationType=...&recommendationId=...` on a fresh session mounts the detail modal at the same time as the gate, and the higher-z modal's content intercepted pointer events meant for the gate's own dismissal checkbox. A safety control must always win. Fixed by raising it to `z-[150]` (now the strict maximum, pinned by `tests/unit/safety-gate-stacking-priority.test.ts` — that test scans every `fixed inset-0 z-[N]` overlay in the app rather than hardcoding "150", so a future overlay added above it fails the test instead of silently reintroducing the bug).

### Confirmed-fine, left as-is

- The lone `group.id === "matched-suggested-guides"` string-literal check (`report-submission-support-page.tsx`) distinguishing a Microcard resource group from a Rights Content one — not a typed discriminant, but not a bug either; changing `TriageResourceGroup` would ripple into the legacy static builders it's shared with (`report-review-onboarding-pages.tsx`, `report-builder-view-model.ts`), out of this phase's scope.
- 3 of the Microcard CTA vocabulary's 7 types (`view_legislation_source`, `view_support_service`, `open_safe_external_link`) have no *published* seed record exercising them — the seed data already has correctly-authored examples of `open_safe_external_link` (`demo-microcard-preparing-for-a-conversation`) and `view_support_service` (`demo-microcard-need-support-now`), just at `needs_update`/`ready_for_review` status, which is deliberate seed-data design (demonstrating every content status). Not changed — doing so would remove Admin's only demonstration of those statuses. All 3 CTA branches are still covered at the unit level (hand-built fixtures, matching this codebase's own established testing convention for this exact scenario) and structurally in the detail-modal test; only live-bundle Playwright coverage of those 3 specific branches is a known, documented gap.

### Tests

Extended `tests/unit/triage-adapters.test.ts` (CTA href resolution parity + rejection of unsafe/unrecognised targets, jurisdiction formatting), `tests/unit/safe-actions.test.ts` (`/emergency` route correction), new `tests/unit/safety-gate-stacking-priority.test.ts`. New `tests/e2e/microcard-cta-safety-smoke.spec.ts` (browser-verified: readable Triage card content with no raw id/admin field/duplicate; `open_internal_route` CTA click-through to the real route; `start_report` CTA click-through to the report flow entry, never implying submission/consent; a `none`-CTA card renders no fabricated button; keyboard open/Escape-close with focus restoration; mobile no horizontal overflow).

## Phase 8.3 — Resource Library and dedicated Micro-card pages now use the mock bundle

Three dashboard routes — `?view=resources` (Resource Library), `?view=microcards` (dedicated Micro-card category/list/detail browsing), `?view=microeducation` (Micro-education lesson browsing) — previously called `src/lib/microeducation.ts` exclusively: a real-backend API client (`/microeducation`, `/microeducation/categories`, `/microeducation/categories/{id}/cards`) with **no mock fallback**. With no backend running in this design/mock phase, every call failed and surfaced a raw `500 Internal Server Error` / "could not be loaded" state directly to the user — even though the exact same `PublishedMicrocard` records these pages want already exist in the generated bundle and already render correctly inside Triage.

New `src/lib/mock/microcard-library-adapter.ts` is a pure, derived view over `MockContentRepository`'s `microcards`/`resourceCategories` domains, reshaped to fit the *existing* `MicroEducationCategory`/`MicroEducationItem` presentational types these three pages already render against — so no page layout, component tree, or design changed, only where the data comes from. `getMockMicrocardCategories()` (only categories with ≥1 published card, sorted by `displayOrder`), `getMockMicrocardsByCategory(id)`, `getMockMicrocards()` (flat, all published), `getMockMicrocardById(id)`. Category colour comes from a small `accentToken` → colour lookup (the contract's `primary`/`success`/`warning`/`destructive`/`secondary` tokens — `PublishedResourceCategory` has no colour fields of its own); a card's `duration`/`format`/`readTimeLabel` are fixed structural defaults (`"quick"`/`"guide"`/`"4 min read"`) since `PublishedMicrocard` has no such dimension — clearly generic, never a per-card fabrication.

**Mock/live boundary**: `MICROCARD_LIBRARY_MOCK_MODE` (`true` for this phase) follows the same module-level boolean-flag convention already established by `REPORT_SUBMISSION_MOCK_MODE` (`report-submission-mock.ts`), rather than inventing a new switching mechanism. `microeducation.ts` itself is untouched and remains the dormant future live-backend path — flipping the flag is the entire migration back to it, no call site shape changes. `ResourcesPage` also had its three independent data loads (content resources, micro-education, the support directory) collapsed into one `Promise.all` that failed all-or-nothing and could surface a raw error message; split into three independent effects so a real-backend failure in the two domains with no mock equivalent (content resources, support directory — out of this phase's scope) degrades to its own existing "not available yet" empty state instead of a page-level error banner, and never blocks the now-working Micro-card section.

Not touched: `MicroCardDetailPage` (`?view=microcarddetail`) — it renders static demo content with no data fetch at all (nothing to fail); the dedicated pages' own in-overlay detail view (opened from `MicroCardsPage`'s category→card flow) is the real "detail" experience objective 7 asked for, and that already works once its data source is fixed. No CTA button was added to the dedicated browse/detail overlay — none exists there today for backend-sourced cards either (confirmed: `activeCardDetail.cta` is computed but was never wired to a rendered button), so adding one would be new behaviour, not a restored default; a Microcard's CTA remains fully safe-and-actionable in the one place it already is — the Triage recommendation detail modal (Phase 7/8.2).
